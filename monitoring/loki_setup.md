# Loki, Promtail and Grafana Monitoring Setup

**Project:** DevOps Command Hub

**Author:** Isaac Ambi

**Date:** 22 November 2026


## 1. Overview

This monitoring stack collects and displays NGINX application logs generated by the application running as a Nomad allocation.

The stack consists of:

| Component | Version | Purpose |
|---|---|---|
| Loki | 3.5.0 | Log aggregation and querying |
| Promtail | 3.5.0 | Log collection and forwarding |
| Grafana | 11.6.0 | Log visualisation and exploration |

### Log flow

1. The NGINX application runs as a Docker task managed by Nomad.
2. Nomad exposes the task's stdout and stderr logs through its allocation logging command.
3. A background log collector writes the output to `monitoring/logs/nginx-nomad.log`.
4. Promtail reads the shared log file, extracts HTTP methods and response status codes, and forwards entries to Loki.
5. Grafana queries Loki and displays the collected logs.

## 2. Environment and deployment

The monitoring stack was deployed using Docker Compose on Ubuntu 24.04 under WSL 2 with Docker Desktop.

The Compose configuration starts three services:

- Loki on port 3100.
- Grafana on port 3000.
- Promtail, which collects the shared Nomad log file.

Validate the Compose configuration:

```bash
docker compose config -q
```

Start the services:

```bash
docker compose up -d
```

Check their status:

```bash
docker compose ps
```

Check Loki readiness:

```bash
curl -sS http://localhost:3100/ready
```

Expected response:

```text
ready
```

## 3. Nomad allocation log collection

The application runs as a Nomad-managed Docker task. Its allocation ID can be obtained with:

```bash
nomad status nginx-app
```

The allocation log stream is collected into a shared file that Promtail can access.

From the `monitoring` directory, set the current allocation ID and start the collector:

```bash
ALLOC_ID="REPLACE_WITH_CURRENT_ALLOCATION_ID"

nohup nomad alloc logs -f "$ALLOC_ID" nginx \
  >> "$PWD/logs/nginx-nomad.log" 2>&1 </dev/null &
```

Replace the placeholder with the current allocation ID.

Check the collected log file:

```bash
tail -n 20 logs/nginx-nomad.log
```

**Environment-specific implementation:** Docker Desktop's internal container log path was not directly accessible from the Ubuntu WSL filesystem. The Nomad allocation log stream was therefore used as the collection source. This keeps the setup compatible with the local WSL environment without claiming direct access to Docker's internal log files.

## 4. Promtail configuration

Promtail reads:

```text
/var/log/nomad/*.log
```

This path is mapped to the project's local `monitoring/logs` directory through Docker Compose.

The configuration assigns the following labels:

| Label | Value or purpose |
|---|---|
| `job` | nginx |
| `app` | devops-command-hub |
| `environment` | local |
| `source` | nomad-allocation |
| `method` | Extracted HTTP method |
| `status` | Extracted HTTP response status |

A regular-expression pipeline extracts the HTTP method, request path and response status code from NGINX access log entries. The method and status are promoted to labels for filtering in LogQL.

Promtail sends the logs to:

```text
http://loki:3100/loki/api/v1/push
```

## 5. Grafana configuration

Grafana is available at:

```text
http://localhost:3000
```

The Loki data source was configured with the following server URL:

```text
http://loki:3100
```

The internal Docker Compose service name `loki` allows Grafana to reach Loki over the Compose network.

The data source connection was tested successfully using Grafana's **Save & test** function.

## 8. Troubleshooting and lessons learned

### Issue 1: Docker container log path unavailable in WSL

**Problem:** The Docker log path returned by `docker inspect` was inside Docker Desktop's internal Linux filesystem and could not be read directly from the Ubuntu WSL environment.

**Resolution:** Used `nomad alloc logs -f` to stream the Nomad task logs into a project directory shared with Promtail.

### Issue 2: Loki ingester not immediately ready

**Problem:** Loki initially returned:

```text
Ingester not ready: waiting for 15s after being ready
```

**Resolution:** Allowed the startup period to complete and checked readiness again. Loki subsequently returned `ready` from its readiness endpoint.

### Issue 3: Grafana query returned an unsupported protocol error

**Problem:** Grafana returned:

```text
unsupported protocol scheme ""
```

**Resolution:** Checked the Loki data source configuration and set its URL to:

```text
http://loki:3100
```

The connection test succeeded and Grafana subsequently displayed the application logs.

## 9. Known limitations

- This is a local development deployment, not a production high-availability logging platform.
- Loki authentication is disabled in this local setup.
- Loki is configured with a 24-hour log retention period.
- The log collector follows a specific Nomad allocation. If the application is redeployed and receives a new allocation ID, the collector must be restarted against the new allocation.
- Logs are collected through the Nomad allocation log stream rather than directly from Docker's internal JSON log files.
- The Nomad and Consul agents are running in development mode.

## 10. Conclusion

The monitoring stack was deployed and tested successfully.

Promtail collected NGINX logs from the Nomad allocation and forwarded them to Loki. Grafana connected to Loki and successfully displayed startup logs, a successful homepage request (HTTP 200), and an intentional missing-page request (HTTP 404).

This verified the complete local log collection, aggregation and visualisation workflow.
